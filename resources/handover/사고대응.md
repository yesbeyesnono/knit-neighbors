# knitup 사고 대응 순서 (해킹·유출이 의심될 때)

2026-11-19 초안. 뚫린 것 같을 때 **무엇부터 할지**만 적은 문서다. 열쇠가 어디 있는지는 `열쇠목록.md`, 평소 운영은 `운영안내서.md`.
값(키·토큰·비밀번호)은 이 문서에도 적지 않는다. 법 조항은 바뀔 수 있으니 실제 사고 때는 개인정보보호위원회 안내를 다시 확인할 것.

## 0. 이런 일이 보이면 사고로 본다
- 텔레그램에 **관리자(admins)가 바뀌었다**는 경보가 왔는데 내가 한 일이 아니다
- 텔레그램 봇 연결 주소가 바뀌었다는 경보(`jigi-remind` guard)
- 콘솔에 내가 하지 않은 조치·공지·지정이 있다(`admin_logs`, `mod_actions`)
- 회원이 "내 정보가 다른 데서 보인다", "보내지 않은 메시지가 갔다"고 알려 온다
- Supabase·GitHub·Cloudflare·Apple·Google 에서 "새 기기 로그인", "비밀번호 변경" 메일이 왔는데 내가 한 일이 아니다
- 비용이 갑자기 뛴다(AI 호출, 영상, 데이터 전송)
- 공개 저장소에 비밀 값이 올라간 것을 발견했다

## 1. 처음 30분 — 더 나가지 않게 막기
순서대로. 원인을 찾는 것보다 **막는 것이 먼저**다.

1. **의심되는 계정의 비밀번호를 바꾸고 모든 기기에서 로그아웃**(구글·Supabase·GitHub·Cloudflare·Apple·Codemagic). 2단계 인증이 꺼져 있으면 켠다.
2. **관리자 목록 확인**: 콘솔 › 시스템. 모르는 계정이 있으면 지운다(`admins` 표). 관리자 세 명 말고는 없어야 한다.
3. **열쇠 폐기·재발급**(아래 2절). 어느 열쇠가 샜는지 모르면 서버 열쇠부터.
4. **필요하면 앱을 멈춘다**: `app_config.min_version` 을 아주 높은 값으로 올리면 모든 앱이 "업데이트 필요" 화면에서 멈춘다(되돌리려면 원래 값으로). 데이터가 계속 빠져나가는 중일 때만 쓴다.
5. **증거를 남긴다**: 화면 캡처, 받은 메일, 시각. 지우거나 고치기 전에.

## 2. 열쇠별 폐기 방법 (값은 `열쇠목록.md` 의 자리에서)
| 샌 것 | 어디서 바꾸나 | 바꾼 뒤 할 일 |
|---|---|---|
| Supabase 서버 열쇠(secret key) | Supabase › Project Settings › API Keys › 그 열쇠 삭제 후 새로 | 백업 저장소의 `SUPABASE_SERVICE_KEY` 다시 넣기 |
| DB 비밀번호 | Supabase › Database › Reset database password | 백업 저장소의 `SUPABASE_DB_URL` 다시 넣기 |
| 앱에 든 공개 열쇠(publishable) | 공개용이라 새는 것이 아님. 다만 악용이 심하면 새로 만들고 앱을 다시 배포 | 앱·콘솔의 `SB_KEY` 교체 → 새 버전 |
| Edge Function 열쇠(AI·텔레그램·푸시·Cloudflare Stream) | 각 서비스에서 Roll/Revoke → Supabase › Edge Functions › Secrets 에 새 값 | 해당 기능 한 번 시험 |
| `jigi_config.hook_secret` | SQL 로 새 임의 값으로 교체 | 예약 작업이 도는지 확인(콘솔 › 자동 메시지) |
| 백업 저장소 열쇠(R2·잠금 암호) | Cloudflare › R2 › API 토큰 Roll · GitHub Secrets 교체 | 백업 한 번 손으로 돌려 초록 체크 |
| Apple 로그인·푸시·Codemagic 열쇠(.p8) | Apple Developer › Keys 에서 Revoke 후 새로 | `tools/apple-secret.js` 로 시크릿 다시 만들기 · Supabase/Codemagic 에 넣기 |
| 안드로이드 서명 열쇠 | Play Console › 앱 서명 › 업로드 키 재설정 요청 | 새 키로 다음 빌드 |

## 3. 피해 확인 — 무엇이 얼마나 나갔나
- **누가 무엇을 봤나**: `access_logs`(1급 데이터 조회 기록) · `admin_logs`(콘솔 조치) · `mod_actions`
- **서버 기록**: Supabase › Logs(API·Auth·Postgres·Edge Functions). 보관 기간이 짧으니 바로 내려받을 것
- **계정 기록**: 구글·GitHub·Cloudflare 의 로그인 기록(기기·위치·시각)
- **무엇이 바뀌었나**: 서버 구조는 `supabase/snapshot/` 과 지금을 대조(`tools/backup/snapshot.sql` → `make_snapshot.py` → `git diff`). 권한은 `supabase/tests/permissions_test.sql` 을 다시 돌린다
- 정리할 것: 유출된 항목(이메일·닉네임·위치(200m 격자)·채팅·배송지·사진), 회원 수, 기간, 경로

## 4. 되살리기
- 데이터가 지워지거나 바뀌었으면: `knitup-backup` 저장소의 날짜별 백업(30일) → 그 저장소 README '되살리기'. 운영 서버에 통째로 덮어쓰지 말고 필요한 줄만 꺼내 넣는다
- 사진: Cloudflare R2 보관함 `knitup-backup`(회원 사진은 잠금 암호로 풀기)
- 영상: Cloudflare Stream 에만 있다(백업 없음)
- 앱 코드가 오염됐으면: 믿을 수 있는 커밋으로 되돌려 새 빌드를 내고, `app_config.min_version` 으로 옛 버전을 막는다

## 5. 신고와 통지 (개인정보가 나갔을 때)
- **72시간 안에**: 유출을 안 때부터 72시간 안에 해당 회원에게 알리고, 다음 중 하나면 개인정보보호위원회(또는 한국인터넷진흥원)에도 신고한다 — ① 1천 명 이상 ② 민감정보·고유식별정보 포함 ③ **외부의 불법 접근(해킹)으로 인한 유출**
  - 신고: 개인정보 포털(privacy.go.kr) › 유출 신고 · 전화 118
- **회원에게 알릴 내용**: 유출된 항목 · 시점과 경위 · 회원이 할 수 있는 조치(의심 메시지 주의 등) · 우리가 한 조치 · 문의처(knitup.official@gmail.com)
- **알리는 방법**: 앱 전체 알림(콘솔 › 공지·알림 보내기) + 이메일. 문구는 사실만, 줄이거나 꾸미지 않는다
- 스토어 심사·제휴 공방·작가에게 영향이 있으면 따로 알린다
- 법률 판단이 필요하면 변호사에게 먼저 묻는다(신고 기한은 그대로 간다)

## 6. 끝난 뒤
- 원인과 고친 것을 `작업기록_전체.md` 에 날짜와 함께 적는다
- 같은 길이 다시 열리지 않게: 권한 시험에 한 줄, 필요하면 경보 추가
- 이 문서에서 실제와 달랐던 부분을 고친다
